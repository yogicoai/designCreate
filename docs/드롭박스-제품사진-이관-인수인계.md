## 5. 설계 결정 — 라벨을 일부러 확정하지 않았다

사용자가 **"폴더에 제품 정보가 정확히 입력됐다는 보장이 없다"** 고 지적했고, 실측해보니 사실이었다.

파일명에 영문 제품명이 박힌 644장으로 폴더명을 대조한 결과:

| 폴더 | 일치율 | 비고 |
|---|---|---|
| 미디·더블·피라미드·팟·허기보·버블 | 100% | 신뢰 가능 |
| 라운저 96% · 서포트 94% | 높음 | 신뢰 가능 |
| 맥스 77% · 미니 75% | 주의 | |
| **슬림** | **18%** | **41장이 파일명에 `midi`** |
| **롤 닷** | **0%** | 6장 전부 `LG-miniroll-*` |
| 롤맥스 33% · 카터필러_롤미디 25% · 인물 0% · 프라임 0% | 낮음 | |
| 샐리필·도기보·롤메이트·모듀·메이트·오토만 | 판정불가 | 파일명 단서 0 |

게다가 **파일명 단서가 있는 건 전체의 7%뿐**이고, 나머지 93%는 `DSC00145.jpg` 같은 카메라 일련번호다.
그리고 한 장에 여러 제품이 나오는 사진이 흔하다(`simu_sp_image_support_pyramid_aquablue.png`) —
**"사진 1장 = 제품 1개"라는 전제 자체가 틀렸다.**

→ 그래서 **`sub`(확정 라벨)를 `null` 로 비워두고 근거만 따로 적는 구조**로 갔다.
나중에 검수 화면에서 `labelStatus: 'conflict'` 부터 훑어 `sub` 를 채우면 된다.
`sourcePath` 에 드롭박스 원본 경로가 남아 있어 언제든 되돌아갈 수 있다.

## 6. 데이터 스키마 (`dropbox_assets` 컬렉션)

```js
{
  url:          'https://yogibo.openhost.cafe24.com/web/design/product/midi/midi_0001.jpg',
  title:        'DSC_0128',          // 원본 파일명(확장자 제외)
  width: 0, height: 0,               // 미측정 — 필요하면 나중에 백필
  sub:          null,                // 확정 제품 라벨 — 검수 화면에서 채운다
  folderHint:   '미디',               // 근거① 드롭박스 폴더명 (분류로 쓰지 말 것)
  filenameHint: ['midi'],            // 근거② 파일명에서 찾은 제품 토큰
  labelStatus:  'agree',             // agree | folder-only | conflict
  sourcePath:   '미디/DSC_0128.jpg',  // 드롭박스 원본 상대경로 — 멱등 키 (unique 인덱스)
  sourceName:   'DSC_0128.jpg',
  source:       'dropbox-product',
  active: true, createdAt: Date,
}
```

`category` / `tags` 는 없다 — 컬렉션 자체가 '드롭박스 파일'이라 분류 칸이 필요 없다.

FTP 경로: `{FTP_REMOTE_DIR}/product/<슬러그>/<슬러그>_<4자리연번>.<확장자>` — **유지 확정**.

읽기는 `src/lib/queries.ts` 의 `getDropboxAssets()` / `getDropboxSummary()`,
쓰기는 `/api/dropbox` (GET 목록+집계 · PATCH 라벨확정 · DELETE 숨김).
**삭제는 없다** — 원본이 드롭박스에 그대로 있고 `sourcePath` 로 되돌아갈 수 있어서 숨김이면 충분하다.

## 7. 반드시 알아야 할 함정 8개

### ① cafe24 FTP 가 대량 업로드 중 연결을 끊는다
`ECONNRESET` 이 수백 장마다 터진다. 첫 실행은 이것 때문에 통째로 죽었다.
지금은 `withFtp()` 가 재연결 + 최대 4회 재시도로 감싸고 있고, **실제로 두 번 복구되는 것을 확인했다.**
업로드는 절대경로로 보낸다 — 재연결로 cwd 가 초기화돼도 엉뚱한 곳에 안 떨어지게.

### ② `lib/ftp.ts` 의 `sanitizeFilename` 은 한글 파일명을 파괴한다
`[^a-zA-Z0-9_-]` 를 전부 `_` 로 바꾸므로 한글명은 통째로 날아가 `upload_<타임스탬프>` 가 되고,
**같은 밀리초에 여러 장이면 덮어쓴다.** 그래서 이 스크립트는 파일명을 `<슬러그>_<연번>` 으로 직접 짓고
원본명은 `title` / `sourceName` 에 보존한다. 다른 대량 업로드를 만들 때도 같은 주의가 필요하다.

### ③ 드롭박스 파일이 전부 "온라인전용"이다 — **읽은 뒤 되돌리기는 사람이 해야 한다**
로컬 동기화 경로는 있지만 디스크 블록은 0이다. **읽는 순간 내려받아져 디스크를 차지한다.**

⚠ **정정 (2026-09-21 실측): `attrib +U -P` 로는 회수되지 않는다.**
처음 인수인계에는 "회수되는 것 검증했다" 고 적혀 있었으나 실측 결과는 반대였다.
메이트 폴더(1,077개)에 `attrib +U -P ... /S` 를 걸고 12초 뒤 확인하니 **온라인전용 0개 · 로컬 4.39GB 그대로.**
제품사진의 온라인전용 9,067개도 회수된 게 아니라 **애초에 안 읽은 파일**이었다.

온라인전용 파일의 속성은 `Archive, SparseFile, ReparsePoint, Offline` 이다 —
**SparseFile + ReparsePoint 는 드롭박스 동기화 엔진이 만드는 것이라 attrib 로 못 바꾼다.**
(OneDrive 의 Files On-Demand 에는 attrib +U 가 먹지만 드롭박스는 다르다.)

**회수 방법 — 탐색기에서 폴더 우클릭 → 「온라인 전용으로 설정」.** CLI 로 되는 방법이 없다.
- 원본은 클라우드에 그대로 남는다. 이 PC 의 로컬 사본만 비운다.
- 공유 폴더여도 이 PC 에만 적용된다 — 팀원 컴퓨터엔 영향 없다.
- **「삭제」와 헷갈리지 말 것** — 공유 폴더라 팀 전체에서 지워진다.

실측 경과: 1차~A안까지 원본 34.7GB 를 읽었고, `--unpin` 을 매 폴더 걸었지만
C: 여유가 47.1GB → 16.6GB 로 줄었다. 큰 폴더를 돌리기 전에 **반드시 디스크 여유를 먼저 확인**하고,
읽고 난 폴더는 사람이 우클릭으로 비워야 다음 작업을 할 수 있다.

스크립트의 `--unpin` 은 해가 없어서 남겨뒀지만 **효과는 없다고 봐야 한다.**

### ④ 샐리필은 제외 대상이다
4,947장으로 전체의 52% 인데 파일명 단서가 0이라 검증이 불가능하다. 사용자가 **"빼도 된다"** 고 명시했다.

### ⑤ cafe24 FTP 에 파일 크기 한계가 있다 — `552 Transfer aborted. File too large`
실측 2026-09-21: **16.6MB 는 통과, 53.5MB 는 거부.** 정확한 한계는 그 사이 어딘가다.
1차 배치 1,687장 중 18MB 초과는 14장(0.8%)뿐이라, 미리 다 줄이면 멀쩡한 사진까지 손해다.
→ `uploadOne()` 이 **원본으로 먼저 올리고 552 가 날 때만 줄여서 재시도**한다.
축소는 긴 변 4500px, 원본 포맷 유지(png 는 png 로 — 확장자와 내용이 어긋나면 안 된다).
줄인 건 `resized: true` / `originalBytes` / `uploadedBytes` 로 남는다. 1차 배치에서 7장이 이 경로를 탔다.
(어제 미디 265/270, 허기보 97/222 로 끝난 것도 일부는 이것 때문으로 보인다.)

### ⑥ sharp 가 큰 사진을 연속으로 줄이면 프로세스가 조용히 죽는다
**이것이 "exit 127 로 죽음" 의 정체다.** 실측 2026-09-21: 미디의 46~52MB 사진 3장을
연달아 축소하다 세 번째에서 종료 코드만 남기고 사라졌다(완료 줄도 안 찍힘).
원본이 12,769×9,579 = **122메가픽셀** 이라 raw 로 펴면 장당 약 367MB 인데,
libvips 가 기본적으로 디코딩 결과를 캐시에 쥐고 있어 연속 처리에서 쌓인다.

```js
sharp.cache(false);      // 한 장씩 처리하는 스크립트엔 캐시가 무의미하다
sharp.concurrency(1);    // 큰 이미지에서 스레드당 버퍼가 곱절로 든다
sharp(abs, { sequentialRead: true, limitInputPixels: 500_000_000, failOn: 'none' })
```
이 셋을 넣으니 같은 3장이 완주했다. **다른 대량 이미지 스크립트에도 같은 주의가 필요하다.**


### ⑦ ★가장 중요★ ECONNRESET 이 조용히 파일을 자른다 — HTTP 200 으로는 절대 못 잡는다
**2026-09-21 사고:** 1차 배치 1,687장을 올리고 `check-product-photos.mjs --all` 이 "1,687 / 실패 0"
을 찍었는데, 실제로는 **1,122장(66.8%)이 잘려 있었다.** 심한 것은 14.1MB 원본이 0.77MB(5%)였고
총 5.2GB 가 유실됐다. 잘린 JPEG 도 서버는 200 으로 내주기 때문에 접근 확인만으로는 멀쩡해 보인다.

원인: cafe24 가 전송 중 데이터 소켓을 끊는데(함정 ①), basic-ftp 가 그것을 **항상 예외로 던지지는
않는다.** 서버가 데이터 커넥션을 닫으면 전송이 정상 종료된 것으로 보여 부분 파일이 "성공" 으로 남는다.
로그의 `↻ 연결 끊김` 은 예외가 난 경우만 찍힌 것이고, 조용히 잘린 쪽은 흔적조차 없다.

**대책 — 올린 뒤 반드시 크기를 대조한다.**
```js
await withFtp((c) => c.uploadFrom(Readable.from(buf), dest));
const remote = await withFtp((c) => c.size(dest));
if (remote !== buf.length) { /* 잘렸다 — 다시 올린다 */ }
```
`scripts/rebuild-dropbox-assets.mjs` 의 `putVerified()` 가 이것이다.
검증도 HTTP 200 이 아니라 **전체 픽셀 디코딩**(`sharp(buf).raw().toBuffer()`)까지 해야 한다.

### ⑧ macOS 리소스 포크(`._이름.jpg`)가 이미지인 척 섞여 있다
맥에서 만든 파일 옆에 남는 메타데이터 껍데기다. 확장자가 `.jpg` 라 확장자 필터를 통과하지만
이미지가 아니라 sharp 가 "unsupported image format" 을 던진다. 더블 폴더에서 10개가 딸려 들어왔다.
수집기에 `/(^|[\/])\._/` 제외를 넣어뒀다. 이미 들어온 10건은 숨김 처리(`active:false`).

## 9-1. 라벨 확정이 가능한 범위 (2026-09-21 치수 대조)

| 구분 | 판별 | 근거 |
|---|---|---|
| 팟 vs 드롭 | **가능 · 사람 없어도 됨** | 세로/가로 팟 1.12 (95×85) vs 드롭 0.88 (75×85) — 27% 차이 |
| 맥스 vs 미니 | 가능 (사람 필요) | 170 vs 85 — 2배 |
| 맥스 vs 미디 | 가능 (사람 필요) | 170 vs 125 — 1.36배 |
| **미디 vs 슬림** | **불가능** | 125 vs 130 — **4% 차이**. 촬영팀도 구분 못 했다(슬림 폴더 41장이 midi 파일명) |
| 도기보·모듀·오토만·프라임·신제품·HDC영창 | 판별 불가 | **제품 DB 에 치수 등록 자체가 없다.** 2차 배치의 절반(1,180장) |

→ 형태가 같은 무리는 DB 의 `sameShapeAs` 로 확인할 수 있다 (Slim/Midi/Mini 는 `sameShapeAs: 'Max'`).
→ **비율이 절대 크기보다 강한 단서다** — 스케일 앵커(사람)가 없어도 쓸 수 있기 때문.
